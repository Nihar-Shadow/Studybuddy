1.1 What StudyBuddy Does
StudyBuddy is an Odia-first, local-first agentic tutoring platform built for
Class 9 students in rural, low-connectivity regions of Odisha, India (modeled
after the persona "Sunita"). Sunita speaks Kui or Odia at home, attends an
Odia-medium government school, and only has access to a low-end shared smartphone
for approximately 1 hour in the evening over weak or intermittent 2G/3G connectivity.

Existing EdTech tools fail Sunita because they:
- Demand high-bandwidth cloud connectivity for video streams and API calls.
- Default to English or Hindi, lacking Odia scientific vocabulary.
- Operate as generic chatbots without memory of what the student has mastered or
  struggled with.

StudyBuddy solves this by running 100% locally on a community laptop or classroom
hub (Ollama + Express) requiring zero cloud subscriptions or API keys. It accepts
questions in Odia (native script or transliteration) and English via text or voice,
routes Odia to a dedicated 2B model (dhee-odia) and English to qwen3:4b, validates
every answer against a 2,400-line Odia scientific language policy, tracks concept
mastery using the SM-2 spaced repetition algorithm, and streams live telemetry to
a teacher dashboard via Server-Sent Events (SSE).

SECTION 2: TOP-DOWN TECHNOLOGY STACK ANALYSIS
================================================================================

2.1 Presentation Layer: Vanilla Web Stack
- Implementation: Semantic HTML5, Vanilla CSS3, Vanilla ES6+ JavaScript.
- Why Used: Low-end Android devices (1GB-2GB RAM) experience massive garbage
  collection stuttering and memory thrashing when parsing multi-megabyte React or
  Next.js bundles. The entire StudyBuddy frontend is under 200KB uncompressed,
  enabling instantaneous rendering on low-tier hardware.
- Key Files:
  - public/index.html: Main student app shell.
  - public/styles/variables.css: HSL-tailored color tokens, dark/light theme variables.
  - public/styles/layout.css: Responsive mobile-first flexbox/grid layout.
  - public/vendor/d3.min.js: D3.js v7 for force-directed concept graphs.
  - public/vendor/chart.umd.min.js: Chart.js for real-time teacher analytics.

2.2 Frontend Client Architecture & Speech
- Client Controllers:
  - public/scripts/chat.js: Form submit interceptor, auto-scroll, message injection.
  - public/scripts/agent.js: SSE stream reader, thinking indicator, tool badges.
  - public/scripts/speech.js (970 lines): Production-tested Web Speech API TTS
    controller. Maps Odia to or-IN, strips markdown before speaking, handles word
    boundaries, and provides fallback handling.
  - public/scripts/voice.js: Web Speech STT controller with microphone audio waveform
    visualizer.
  - public/sw.js: Service Worker precaching shell assets (cache name: studybuddy-v7).
    Guarantees the app shell loads when disconnected from the hub.

2.3 Backend API Layer: Node.js & Express 4.22.1
- Implementation: Express 4.22.1 over Node.js (CommonJS).
- Why Used: Non-blocking asynchronous I/O is ideal for holding multiple long-lived
  Server-Sent Events (SSE) connections with near-zero memory footprint.
- Selective Gzip Compression:
  In server.js (lines 71-80), compression({ level: 6, threshold: 1024 }) is configured
  to compress responses >1KB. Crucially, paths in SSE_PATHS (['/chat', '/api/events'])
  are explicitly excluded. Standard gzip buffers chunks until a block size is reached;
  excluding SSE prevents buffering and delivers real-time token streaming.

2.4 AI/ML Inference Layer: Local Ollama (Port 11434)
- Engine: Ollama v0.35.0 running on localhost:11434.
- Dual-Model Local Routing (agent/models.js):
  - dhee-odia:latest (1.8 GB, 2B Qwen-based): Pre-trained on Odia linguistic corpora.
    Handles all queries containing Odia Unicode (\u0b00-\u0b7f) or Odia language selection.
  - qwen3:4b (2.5 GB): High-capacity reasoning model. Handles English/Hindi questions,
    complex multi-tool agent planning, and structured JSON generation.
- Keep-Alive Optimization: OLLAMA_KEEP_ALIVE=60m keeps models resident in GPU/VRAM to
  eliminate 10-second cold-load latencies during live student sessions.

2.5 Data & Persistence Layer: Atomic Flat-File JSON
- Files: data/progress.json, data/cache.json, data/taxonomy_learned.json.
- Implementation (agent/progressStore.js):
  - Atomic Disk Writes: Data is written to a temporary file (progress.json.tmp) and
    renamed atomically to progress.json using fs.renameSync. This prevents data
    corruption during sudden power loss or process kill.
  - Corruption Recovery: If JSON.parse fails on startup, the corrupted file is renamed
    to progress.json.corrupt.<timestamp> and a fresh valid schema is initialized.
- SM-2 Spaced Repetition: Implements SuperMemo SM-2 to update repetitions, interval,
  and ease factors after every quiz attempt.

3.2 Authentication & Authorization Flow
```
User navigates to "/"
       |
       v
Check req.session.role in server.js
       |
       +---> If no session -> 302 Redirect to "/login"
       |
       +---> If role === 'student' -> 302 Redirect to "/app"
       |
       +---> If role === 'teacher' -> 302 Redirect to "/teacher"

POST /login with { pin: "1234" }
       |
       v
auth.js verifies against process.env.STUDENT_PIN / TEACHER_PIN
       |
       +---> Invalid -> 401 { error: "Invalid PIN" }
       |
       +---> Match -> Sets req.session.role, studentId, studentName
                      Returns 200 { success: true, role: "student" }
```

3.3 Multi-Tier Safety Guardrail Flow
```
User sends Odia Question ("ଆଲୋକ ସଂଶ୍ଳେଷଣ କ’ଣ?")
       |
       v
Grounding: Retrieve verified facts from lib/class9Knowledge.js
       |
       v
Inference: Call Ollama (dhee-odia) with SCERT grounded facts
       |
       v
Language Policy Validation (lib/languagePolicy.js):
   - Check Odia Unicode purity
   - Verify scientific terminology (reject corrupted terms)
   - Fact validation (prevent false science statements)
       |
       +---> PASS -> Stream tokens directly to client
       |
       +---> FAIL -> Trigger 1 Corrective Repair Prompt to Ollama
                        |
                        +---> REPAIR PASS -> Stream repaired answer
                        |
                        +---> REPAIR FAIL -> Stream SCERT Verified Fallback Facts
```

SECTION 4: FILE-BY-FILE MODULE DEEP DIVE & CODE WALKTHROUGH
================================================================================

4.1 Application Entry: server.js (271 lines)
- Responsibility: Express bootstrap, environment validation, session configuration,
  route registration, SSE teacher broadcasting, and Ollama model pre-warming.
- Security Validation (lines 20-39):
  In production (NODE_ENV=production), refuses to boot if SESSION_SECRET is missing,
  or if STUDENT_PIN or TEACHER_PIN use default insecure values ('1234', '9999').
- SSE Broadcasting (lines 226-257):
  Maintains a Set of active teacher response streams (sseClients). Hooks into
  progressStore.on('data_updated') to broadcast real-time student activity to the
  teacher dashboard instantly.
- Model Warmup (line 269):
  Executes warmUpModels() upon server start to ensure models are compiled and resident
  in VRAM before the first student request arrives.

4.2 Route: routes/chat.js (39,579 bytes)
- Responsibility: Main doubt resolution streaming controller.
- Key Functions:
  - resolveTopicAndConcept(query, history): Matches user input against curriculum
    taxonomy keywords using trie.js and dynamicTaxonomy.js.
  - POST /chat: Validates request body { message, language, studentId, level }.
    Sets Content-Type: text/event-stream. Checks smartCache; if cache hits, streams
    cached response with latency tag. If cache misses, calls llmProvider, validates
    output against languagePolicy, streams SSE data chunks, and mutates student
    confidence state.

4.3 Route: routes/agent.js (1,693 bytes)
- Responsibility: POST /agent autonomous multi-tool endpoint.
- Logic:
  Extracts query and history, binds session studentId, and executes runParallelAgent()
  or runAgentLoop() from agent/agentLoop.js. Returns structured JSON containing
  plan, toolExecutions, synthesizedAnswer, and nextStudy recommendation.

4.4 Route: routes/quiz.js (28,373 bytes)
- Responsibility: Quiz generation and submission grading.
- POST /quiz:
  Accepts { topic, concept, count, language }. Calls generate_quiz tool. Employs
  parseJSON.js to parse the LLM's MCQ array. Validates that exactly 1 correct answer
  exists per question.
- POST /quiz/submit:
  Accepts { studentId, topic, concept, answers }. Grades each response, calculates
  percentage score, updates SM-2 repetition schedule in progressStore.js, and
  updates concept confidence (e.g. marking <60% scores as needs_review).

4.5 Route: routes/auth.js (5,351 bytes)
- Responsibility: Authentication, PIN verification, session destruction.
- Middlewares Exported:
  - requireAuth: Ensures req.session.role exists; redirects to /login if missing.
  - requireTeacher: Ensures req.session.role === 'teacher'; returns 403 or redirects.

4.6 Agent Core: agent/agentLoop.js (24,589 bytes)
- Responsibility: Autonomous planning and tool execution engine.
- runParallelAgent(query, context):
  Prompts qwen3:4b to generate a JSON tool execution plan. The model selects from
  the 6 registered tools. Independent tools (e.g. explain_topic and generate_concept_map)
  are executed concurrently using Promise.all(). Gathers all outputs and generates
  a final synthesis.
- runAgentLoop(query, context):
  Deterministic 4-step fallback pipeline. If planning fails or returns malformed
  JSON, safely executes: explain_topic -> validate -> track_progress -> suggest_next_topic.

4.7 Agent Tools: agent/tools.js (32,729 bytes)
- Exports the 6 executable tools:
  1. explain_topic: Generates 3-part structured explanation (intro, steps, takeaway).
  2. generate_quiz: Generates 3-5 MCQs with distractors and explanations.
  3. track_progress: Updates progressStore and emits SSE update event.
  4. suggest_next_topic: Evaluates student history and SM-2 schedules to pick next topic.
  5. ask_socratic_question: Generates 5-step guided inquiry dialogue turns.
  6. generate_concept_map: Builds node and edge graph for D3 rendering.

4.8 Persistence: agent/progressStore.js (15,389 bytes)
- Responsibility: Multi-student state management, SM-2 algorithm, disk persistence.
- Key Methods:
  - ensureStudent(studentId, name): Initializes student profile if new.
  - sm2(studentId, topic, concept, score): Calculates repetitions, interval, and
    ease factor (EF) using SuperMemo SM-2.
  - getWeakConcepts(studentId): Returns concepts with score < 60% or flagged needs_review.
  - getDueReviews(studentId): Returns concepts whose nextReview date <= Date.now().
  - save(): Writes to data/progress.json.tmp and atomically renames to progress.json.

4.9 Domain Knowledge: lib/class9Knowledge.js (90,320 bytes, 1,433 lines)
- Responsibility: Grounding facts for 8 Odisha SCERT Class 9 science topics:
  1. photosynthesis (ଆଲୋକ ସଂଶ୍ଳେଷଣ)
  2. matter (ପଦାର୍ଥ)
  3. states_of_matter (ପଦାର୍ଥର ଅବସ୍ଥା)
  4. evaporation (ବାଷ୍ପୀଭବନ)
  5. water_cycle (ଜଳ ଚକ୍ର)
  6. force_and_motion (ବଳ ଓ ଗତି)
  7. cell (କୋଷ)
  8. respiration (ଶ୍ୱସନ)
- Each topic provides: canonical Odia terms, verified textbook definitions, step-by-step
  processes, common student misconceptions, and pre-compiled fallback answers.

4.10 Guardrails: lib/languagePolicy.js (166,442 bytes, 2,400+ lines)
- Responsibility: Enforces Odia linguistic integrity and scientific validity.
- Key Features:
  - containsOdiaScript(text): Regex validation for Unicode range \u0b00-\u0b7f.
  - validateScientificTerms(text, topic): Detects corrupted transliterations and
    verifies presence of canonical Odia scientific vocabulary.
  - buildRepairPrompt(errorType, originalAnswer, verifiedFacts): Synthesizes targeted
    corrective prompt instructing the LLM to fix the exact validation failure.

and memory footprint of running a Postgres or MongoDB daemon on resource-constrained
laptops.

8.1 Dual-Model Routing Mechanism (agent/models.js)
```javascript
function getModelForLanguage(language, text = '') {
  const isOdia = language === 'or' || 
                 language === 'Odia' || 
                 containsOdiaScript(text);
  if (isOdia) {
    return {
      model: 'dhee-odia:latest',
      temperature: 0.2, // Low temperature for high factual precision
      top_p: 0.9
    };
  }
  return {
    model: 'qwen3:4b',
    temperature: 0.4,
    top_p: 0.9
  };
}
```

8.2 The Hallucination & Terminology Problem in Low-Resource Languages
Small 2B parameter models in low-resource Indic languages frequently produce
phonetic loan-word corruptions (e.g. writing "ଫୋଟୋସିନ୍ଥେସିସ୍" instead of the
canonical Odia curriculum term "ଆଲୋକ ସଂଶ୍ଳେଷଣ").
Furthermore, 2B models can mix up scientific causation (such as claiming plants
take in oxygen to produce food).

8.3 The Multi-Tier Guardrail Implementation (lib/languagePolicy.js)
1. Linguistic Policy Rules: A dictionary of 500+ approved Odisha SCERT scientific
   terms and 200+ banned corruptions.
2. Output Interception: Before the final token stream is verified, the text is
   checked against the active topic's rules.
3. Corrective Repair Prompt: If a corrupted term is found, an immediate zero-shot
   repair prompt is fired:
   "Your previous answer used an incorrect scientific term '[corrupted]'. Rewrite
   the answer in pure Odia replacing it with canonical term '[canonical]'."
4. Deterministic SCERT Fallback: If the repaired answer still fails validation,
   StudyBuddy completely aborts the model's text and serves the pre-compiled,
   verified textbook explanation from lib/class9Knowledge.js.

9.1 PIN Authentication Model
- Why PINs: Rural students do not have individual email addresses, Google accounts,
  or mobile numbers for OTP authentication. A 4-digit PIN allows instant access.
- Roles:
  - student (PIN: 1234 in dev): Access to /app, /chat, /quiz, /progress.

9.2 Security Hardening in server.js
- In production, server.js refuses to boot if default PINs are detected.
- Sessions use httpOnly: true cookies to protect against Cross-Site Scripting (XSS).
- Cookie secure flag is false because local offline community hubs run over plain HTTP
  (http://192.168.x.x:3000) on local Wi-Fi hotspots where SSL certificates cannot be
  verified without internet access.

9.3 Critical Vulnerability & Quality Audit
1. CSRF Protection: Currently, session cookies use sameSite: 'lax', but no CSRF
   tokens are implemented on POST endpoints.
   Severity: Low in local offline network; Medium if deployed to public internet.
   Remediation: Implement csurf middleware before public deployment.
2. In-Memory Session Storage: MemoryStore is used by default.
   Severity: Low for single-machine demo; Sessions reset on server reboot.
   Remediation: Configure session-file-store for persistent session recovery.

SECTION 11: DATA STRUCTURES, ALGORITHMS & PEDAGOGICAL BUSINESS LOGIC
================================================================================

11.1 Topic Keyword Trie (agent/trie.js)
- Purpose: Class 9 curriculum keyword matching across thousands of Odia terms.
- Implementation: Standard prefix Trie where each node represents a character.
- Complexity: Search time is O(K) where K is the query word length, completely
  independent of the number of registered curriculum keywords (N).

11.2 SuperMemo SM-2 Spaced Repetition Algorithm (agent/progressStore.js)
- Formulas Implemented:
  1. EF' = EF + (0.1 - (5 - q) * (0.08 + (5 - q) * 0.02))
     Where EF is clamped to a minimum of 1.3.
  2. If score q >= 3 (Pass):
     - If repetitions == 0 -> interval = 1 day
     - If repetitions == 1 -> interval = 6 days
     - If repetitions > 1  -> interval = round(previous_interval * EF)
  3. If score q < 3 (Fail):
     - repetitions = 0
     - interval = 1 day
- Benefit: Guarantees that Sunita is prompted to review difficult concepts precisely
  at the point of forgetting.

SECTION 12: DESIGN DECISIONS, ARCHITECTURAL TRADE-OFFS & CODE QUALITY AUDIT
================================================================================

12.1 Key Design Decisions & Trade-Offs
1. Local Ollama vs. Cloud API (OpenAI/Anthropic):
   - Decision: 100% local Ollama inference.
   - Trade-off: Higher token latency (10-15s vs 2s on cloud) and lower model parameter
     capacity (2B/4B vs 70B+), but guarantees zero subscription cost and 100% offline
     functionality in rural villages with zero internet.
2. Flat-File JSON vs. SQLite / PostgreSQL:
   - Decision: Atomic file-backed JSON store (progressStore.js).
   - Trade-off: Not suitable for 10,000 concurrent writes, but completely removes
     C++ compilation dependencies, native database drivers, and setup friction on
     school laptops.
3. Vanilla JS vs. Modern Frontend Framework (React/Vite):
   - Decision: Vanilla HTML5, CSS3, and ES6 modules.
   - Trade-off: Manual DOM manipulation in scripts/agent.js, but ultra-lightweight
     (<200KB bundle) running smoothly on 1GB RAM Android Go phones.

12.2 Known Architectural Gaps (P0 & P1 Backlog)
1. Hidden Agent Toggle (P0 Blocker):
   In public/index.html (line 99), <button id="agent-toggle"> is hidden with
   style="display:none;". The multi-tool planner is fully functional on the backend
   (/agent), but browser users only trigger single-turn /chat unless unhidden.
2. Missing IndexedDB Mutation Queue (P1 Blocker):
   In public/sw.js (lines 135-152), failed POST requests return HTTP 503 when the
   client disconnects from the laptop hub. An IndexedDB queue is required to buffer
   quiz answers and replay them upon reconnection.
